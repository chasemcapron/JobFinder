# Decisions

One line each: decision — why.

- Next.js 16.4 with `cacheComponents: false` — every page is per-user and request-time, so static-shell prerendering adds complexity with no benefit for a single-user app.
- Embedded Postgres (PGlite) when `DATABASE_URL` is empty (dev only) — the app runs locally with zero setup and uses the same Drizzle schema and migrations as Neon/Supabase.
- `postgres` (postgres-js) driver with `prepare: false` — works with both Neon and Supabase, including transaction-mode pooled URLs.
- Migrations live in `drizzle/` and are applied with `npm run db:migrate` (PGlite applies them on startup) — keeps schema changes explicit instead of running them during the Vercel build.
- `job_matches`, `applications`, `email_log`, `target_companies` are per-user; `jobs` is shared — job postings are the same for everyone, matches are not.
- Profile preferences are typed columns on `profiles` (not a JSON blob) — easier to query and validate.
- Added a `search_runs` table — needed to show per-source failures and run history in the UI.
- Auth.js v5 (next-auth@beta) with JWT sessions + Drizzle adapter — JWT is required for the credentials-based demo login; the adapter still stores users and Google accounts.
- A "demo account" sign-in (credentials provider, no password) is enabled only when Google OAuth isn't configured and NODE_ENV isn't production (override with ENABLE_DEMO_LOGIN) — lets the app run end to end before OAuth setup without exposing anything in production.
- Dev-only fallback AUTH_SECRET when unset outside production — `npm run dev` works with no .env; production still refuses to start without one.
- Google provider uses `access_type=offline` + `prompt=consent`, and a signIn event re-saves tokens on every Google login — the adapter only stores tokens on first link, and Sheets needs a fresh refresh token.
- Seeded target companies: greenhouse:stripe, greenhouse:figma, lever:spotify, ashby:ramp, ashby:linear — each verified live on 2026-10-15; lever:netflix and lever:plaid returned 404 so were left out.
- Target companies can be entered as `ats:slug` or by pasting a board URL — less friction than looking up slugs.
- Sheet setting accepts the full sheet URL and extracts the ID — that's what people have on hand.
- Settings changes that affect ranking bump `profiles.matching_updated_at`, so stale matches get re-scored on the next run.
- Default Claude model is `claude-opus-5-5` (override with ANTHROPIC_MODEL); calls use `effort: "low"` — extraction and scoring are simple structured tasks, and low effort is the cost lever that keeps the default model.
- Claude calls use structured outputs (`betaZodOutputFormat`) + `fallbacks: "default"` (server-side refusal fallback) — guaranteed-valid JSON and no dead end if a classifier declines a resume.
- Resume upload is two steps (extract → review/edit → save); nothing is persisted until "Save profile" — the brief asks to edit the result before saving.
- With no ANTHROPIC_API_KEY, resumes are analyzed by a built-in heuristic (skills dictionary, title-line detection, years-of-experience → seniority) — the app stays usable without a key.
- Upload limit 4 MB, Server Action body limit raised to 5 MB — Vercel rejects request bodies over 4.5 MB.
- pdf.js needs DOMMatrix, normally from @napi-rs/canvas, which has no Windows-ARM64 build; a pure-JS polyfill (@thednp/dommatrix) is used only when the native one can't load — text extraction doesn't render, so it's sufficient.
- Resumes over 60,000 characters are rejected with a message rather than silently truncated.
- Greenhouse/Lever/Ashby adapters were written against live responses captured 2026-10-15 (trimmed copies are the test fixtures); the Adzuna adapter follows its official docs (no key; it's paid). USAJobs was verified live 2026-10-20: `CountryCode` is a country name, remote postings say "Anywhere in the U.S. (remote job)", and grades come in pay plans other than GS (GG and NH map onto the GS scale).
- USAJobs searches ask only for postings open to the public, students and recent graduates (`HiringPath`): about 40% of federal cyber postings are limited to current federal employees, veterans, spouses and similar paths, which an outside entry-level applicant can't use. Postings with no US location are dropped.
- Lever and Ashby don't return a company name, so it's derived from the board slug ("spotify" → "Spotify").
- Ashby's `isRemote` is true for hybrid roles, so `workplaceType` decides remote; Lever uses `workplaceType` too.
- Workday career sites are a fourth target-company type (`workday`, slug `tenant.wdN/site`, site name keeps its case because it names the company). Workday has no public API, so the adapter calls the JSON endpoints the career site's own page uses (`/wday/cxs/{tenant}/{site}/jobs` and the posting path); robots.txt doesn't exclude them. Verified live 2026-10-20 against nine employers (Leidos, Booz Allen, CrowdStrike, Northrop Grumman, RTX, Boeing, Capital One, NVIDIA, Mastercard).
- Workday sites are searched, not listed (no full feed; big sites have 2,000+ postings, listings have no descriptions, pages are 20 max): the profile's top 3 titles, 3 listing pages in all, then details for the best 25 by title (far-too-senior last). Titles aren't used to drop postings, because loose matches include real fits ("Analyst I, Falcon Complete" is CrowdStrike's MDR analyst). That's at most ~30 requests per company per search, inside a 9 s budget so the task returns before the 12 s source timeout.
- Workday's country filter (`locationCountry`, US id `bc33aa31…`, the same on every site) is sent first; sites without it answer 400 (or ignore it), so the search repeats unfiltered and foreign postings are dropped by their listing location before details are fetched.
- Workday company names come from the site name ("Northrop_Grumman_External_Site" → "Northrop Grumman"), else the tenant ("leidos" → "Leidos"): the API's hiring organization is a legal entity ("631 Booz Allen Hamilton_United States") or empty. "Suggest companies" stays on Greenhouse/Lever/Ashby, whose slugs the AI can guess and check quickly.
- Settings offers a fixed list of checked Workday employers (`workday-employers.ts`, 56 sites in five sectors) instead of AI suggestions: Workday URLs (tenant, wdN, site name) can't be guessed. The sites were found from each candidate tenant's robots.txt (it lists the site names; unknown tenants answer 422) and kept only when a live US "security analyst" search answered with security or IT roles (2026-10-20). The list leans to security, defense and IT because the app's one user is in cybersecurity. Its names also replace guessed ones ("ghr.wd1/Lateral-US" is Bank of America, "bah.wd1/BAH_Jobs" Booz Allen Hamilton).
- At most 12 Workday sites per search (`MAX_WORKDAY_SITES_PER_SEARCH`), rotating daily when more are added, and sources run 12 at a time (was 8). A Workday site takes 3-11 s, so without a cap one-click "Add all" could push a run past 60 s. Measured: 5 hosted boards + 12 Workday sites fetched in 11.8 s. Rotation keeps every site visited every few days, well inside the 21-day "closed" cut-off.
- Locations are parsed into city/state/country (ISO-2) with a small gazetteer of major cities and the abbreviations seen in real data ("NYC, SF", "US-SEA"); multi-location postings use the first parseable place for filters; the raw string is kept for display and search. 94% of 1,143 live postings resolve a country.
- Salary: structured fields when the source has them (annualized from hourly/monthly), otherwise parsed from the description (Greenhouse puts pay ranges in the HTML). Adzuna's *predicted* salaries are skipped — they carry extra attribution terms.
- Dedupe key = normalized company + title + place; when two sources have the same job the direct ATS copy wins over USAJobs/Adzuna (richer description, direct apply link).
- Each source "task" (one per target company, one per Adzuna/USAJobs query) runs in parallel (max 8) with a 12s timeout; a failed or slow source is recorded in `search_runs.source_results` and shown in the UI, never failing the run.
- Adzuna turned out not to be free (2026-10), so it stays optional and unset; if a key is ever added, a run makes at most 2 Adzuna queries (and 2 USAJobs queries), built from the top target titles + first preferred location.
- Keyword prefilter: title similarity 40 + skills 35 + keywords 15 + preferences 10, with penalties for remote/level/location mismatches; jobs under 10 aren't saved as matches. Claude re-scores only the top MAX_AI_SCORES_PER_RUN (default 20) jobs that don't already have an AI score newer than the last profile change, in batches of 10.
- Each job's description is cut to 2,500 characters in the Claude scoring prompt — that's where the role summary lives; the rest is mostly boilerplate, and it bounds cost per run.
- Sample/mock postings (`source = "mock"`) are used when MOCK_JOBS=true, or when there's nothing real to query — the app always has something to show offline.
- Jobs not seen by any search in 21 days are hidden from results (treated as closed).
- The refresh API refuses to start a second run for the same user while one is in flight (409).
- Results filtering runs in memory over the user's match rows (max 2,000, newest-seen jobs only) via a pure `filterMatches` — simple, fully unit-testable, and fast at personal scale; only the first 3,000 description characters are loaded for keyword search.
- Filters live in the URL (shareable, back button works, form works without JS); selects apply instantly, the search box debounces 400 ms; keyword search ANDs terms and supports "quoted phrases".
- Location dropdowns are facets built from the actual results (states narrow to the chosen country, cities to the chosen state), with counts.
- Applied jobs are dimmed by default, with "hide" and "only applied" options; also added minimum-score and sort-by-newest, which the brief didn't ask for but cost little.
- In comma lists like "Seattle, Chicago, US", a middle token only becomes the state/region if it really is one (US state, or a non-city elsewhere) — prevents cities leaking into the State filter.
- Sheets rows are written with `values:batchGet` (find the last used row across the mapped columns) + `values.update` at that exact row, not `values.append` — append starts writing at the detected table's first column, which shifts every value when a table doesn't start at A. Unmapped columns are sent as null, which the API skips, so existing cells/formulas are untouched.
- Default mapping is the brief's example (Company A, Title B, Date Applied C, Link D, Location E, Status F); Source and Match score are optional extra fields. Duplicate columns are rejected.
- Text from postings is written with USER_ENTERED, so anything starting with = + - @ gets an apostrophe prefix (stored as text, not run as a formula); the date is left unescaped so Sheets parses it as a date.
- The application is saved before any Sheets call; failures are stored on the row (`sheet_sync_status` = failed + error) and shown with a Retry button. "No sheet set" / "Google not connected" are `not_configured`, not failures. A synced application is never appended twice.
- Status changes and removals only affect the app, not the sheet — the brief only asks to append, and editing someone's own sheet in place is risky without knowing its layout.
- Google access tokens are refreshed server-side from the stored refresh token (60 s before expiry); revoked access or a missing Sheets scope produces a "sign out and back in" message.
- "Test connection" in Settings reads the sheet's tabs and header row, so the user can see which letter holds which column before relying on the mapping.
- `vercel.json` schedules `/api/cron/morning` at 12:00, 13:00 and 14:00 UTC; the route sends only when it's 7 AM in America/Chicago, and the 8 AM invocation retries a run that didn't finish (both DST seasons get a retry). Gated on the hour (not the minute) because Vercel Hobby crons fire anytime within the scheduled hour; Hobby allows 100 once-a-day crons (checked 2026-10-20).
- The search runs in its own cron at 10:00 UTC (`/api/cron/search`), hours before the email: a search with 12 Workday sites plus AI scoring can take most of a 60 s function, and sharing one function with the email meant a slow search could cost the day's email. The email searches inline only when no search succeeded in the last 6 hours.
- Once-per-day is a lease, not a flag: `profiles.digest_claimed_at` is set by compare-and-set before any work and cleared when the run finishes, which is also when `last_digest_date` is set. A run Vercel cuts off leaves the claim behind; after 5 minutes (functions stop at 60 s) the 8 AM retry takes it, skips the search (the likely culprit) and sends from existing matches. The send carries a Resend idempotency key per user and day, so a run cut off after Resend accepted the email can't send it twice. Search runs still "running" after 5 minutes are marked stopped.
- Old data is pruned by the search cron (Neon free is 0.5 GB; jobs are ~4.4 KB each, 14 MB total on 2026-10-20): jobs unseen for 60 days unless someone applied to them (deleting would cascade to the application), and search runs older than 90 days. This is the one place that deletes across users; it's behind CRON_SECRET.
- The cron route rejects every request when CRON_SECRET is unset (503) and compares the bearer token in constant time. `?force=1` skips the hour check for manual testing but still respects once-per-day.
- Settings → Integrations shows a "Morning email" row (Ran today / Scheduled / Missed today / Off) from the latest cron-triggered search run, `last_digest_date` and the latest `email_log` send. A rejected or never-made cron call leaves no row, so absence is the signal: from 8 AM Chicago, no claim for today means "Missed today", with a short guide to the Vercel log codes. Added after the first scheduled morning (2026-10-20) left no trace.
- Digest = up to 10 matches with score ≥ 40 that aren't in `email_log` and aren't applied to; nothing is sent when there are none. If the morning search fails, the digest still goes out from existing matches.
- Follow-up reminders ride on the morning email: an application still `applied` 7-30 days after applying is listed once (`applications.follow_up_sent_at`, set only after a successful send; at most 5, oldest first). The 30-day limit keeps the first email after this shipped from listing old applications. A reminder alone is enough to send the email. `email_log` couldn't be reused: it's unique per user and job, and the job was usually emailed before it was applied to.
- Users are processed sequentially and no new user is started after 35 s, to stay inside the 60 s function limit; fine for a personal app (one or a few users).
- Without RESEND_API_KEY/EMAIL_FROM the email is printed to the server log and still recorded in `email_log` (channel "console"), so the whole flow is testable locally. Adzuna jobs carry the "Jobs by Adzuna" link in the email too.
- Added `/api/digest/preview` (signed-in only) and a Settings link to it — renders what the next digest would contain without sending or logging.
- Error boundaries at two levels: `(app)/error.tsx` inside the app shell, and `app/error.tsx` for failures in the signed-in layout itself (e.g. database unreachable), plus `global-error.tsx`; production shows the error digest for log lookup instead of the hidden message.
- Basic security headers (X-Frame-Options DENY, nosniff, strict referrer, no camera/mic/geolocation) and no `X-Powered-By`.
- `outputFileTracingIncludes` adds pdf.js's worker to the /resume function: pdf.js loads it with a computed import that file tracing can't follow. Verified by uploading a PDF to a standalone build, which (like Vercel) ships only traced files.
- Settings shows each target company's result from the last search (posting count, or the error), so broken slugs are easy to spot.
- README documents that Google OAuth apps in Testing mode get refresh tokens that expire after 7 days — the brief asks for Testing mode, so Sheets sync needs a re-login about weekly; the app says so when it happens.
- `ALLOWED_EMAILS` allowlist checked in the Auth.js `signIn` callback (before the adapter creates a user): the app is single-user and public on Vercel, and Google's Testing-mode test-user list shouldn't be the only gate.
- Accepted `npm audit` moderate (sprintf-js via mammoth → argparse): no patched sprintf-js exists, and argparse is only used by mammoth's CLI, never by the library calls the app makes.
- Design tokens: every color is a CSS variable in `globals.css` (neutrals, accent + `accent-text` for links, and success/warning/danger/info/neutral each with solid, `-bg`, `-fg`, `-border`), plus `shadow-xs/card/raised` and `rounded-control/card/pill`; dark mode swaps the variables, so components never use `dark:` or raw palette colors. Text pairs were checked for WCAG AA in both themes. Badge keeps the old green/amber/red/blue tones as aliases of the semantic ones.
- global-error.tsx and the digest email use literal hex values mirroring the globals.css tokens (global-error replaces the root layout so has no stylesheet; email clients lack CSS variables); the digest shows the score as a colored NN% match pill using the same 75/55/35 thresholds as ScoreBadge.
- Theme C ("Charcoal with colour accents", made more playful): dark-first charcoal tokens; 4-hue palette (pink/orange/blue/green) for meaning only: header stripe (wipes in once), per-section colour (Jobs blue, Applications orange, Resume green, Settings pink) via `data-section` set by `SectionScope`, solid score-tier tiles (green 75+, blue 55+, orange 35+, grey) matching the job-card edge, per-board source chips. Primary buttons, links, focus borders, nav pill and PageHeader/CardHeader tiles follow the section colour; text on solid fills uses `--section-on` (white on blue, charcoal `--ink` on orange/green/pink) to stay AA. Cards lift and buttons press (reduced-motion respected); light tokens kept under `:root[data-theme="light"]`, dark forced via `data-theme="dark"` on `<html>`.
- Match scores use three colours on a calibrated 0-100 scale: green 75+, yellow 50–74, red under 50 (`scoreTier` in `ui.tsx`, shared with the digest email). The keyword matcher's raw points top out around 70–75 for excellent fits, so `calibrateKeywordScore` maps raw 0–75 to 0–95 and eases anything above toward 100. The numbers then read the way people expect, and top matches don't all tie at 100. The digest cut-off is 50, the same as yellow. Job cards get a full 2px outline in the score colour, and stay neutral until a resume exists.
- Type follows the inspiration boards: Bricolage Grotesque for page titles and big numbers, Barlow Condensed in caps (`font-label`, via `Kicker`) for labels on colour bars, tiles and card headings, Geist for body text. Flat solid tiles (`StatTile`, `BarHeading`) carry colour instead of gradients or shadows; white text on blue, charcoal on green/orange/pink keeps every pairing AA.
- The Jobs list shows one card per role: postings with the same company and title (Workday and USAJobs list a role once per city) collapse into the best-ranked one, with "Also in N other places" linking each copy. Counts and the summary tiles count roles. Tiles: new in 24 h, strong (75+) not yet applied, applied this week, interviewing; each links to the view it counts. The full score-colour outline (#14) stays.
- Applications is a pipeline board: Applied, Interviewing, Offer, Closed (rejected + withdrawn) columns under colour bars, status changed with the existing select (no drag and drop: a select works on phones and with a keyboard). Response rate = answered (interview, offer, rejection) / not withdrawn. Cards still marked Applied after `FOLLOW_UP_AFTER_DAYS` (7, shared with the digest reminder) say "No reply in N days".
- The original resume file is stored in Postgres (`resume_files`, bytea, ≤4 MB, one per user) so /resume can preview it. An upload is "pending" until Save promotes it, so nothing changes before the user saves. PDFs are embedded from `/api/resume/file`, which is why `X-Frame-Options` is SAMEORIGIN (plus `frame-ancestors 'self'`) instead of DENY. A .docx is converted with mammoth into a sandboxed `srcdoc` iframe.
- The Resume page edits titles, skills, keywords and skip words as chips (titles as a numbered list with move-up buttons, the top three highlighted because Workday sites are searched for them; no drag and drop, as on the pipeline board). Each list posts as one newline-joined field through the same `parseList` (limits in `resume/limits.ts`), so an unedited draft equals what's saved. "Unsaved changes" compares the draft with the saved profile, ignoring CRLF (form posts send textarea line breaks as CRLF), and shows in the step bar and in a save bar that sticks to the bottom of the screen; closing the tab with unsaved changes asks first. The extract form no longer clears itself, so a failed read can be retried without picking the file again. The saved-file preview moved below the editor.
- US only: `TARGET_COUNTRY` in `location.ts`. Search drops non-US jobs before storing, and the jobs list and digest also hide older non-US rows. Jobs with no parsed country are kept, because in practice they are US postings the parser misses ("Remote in the US", "NYC-HQ", "N/A"). The Country filter and the Adzuna country setting were removed.
- AI runs on Gemini's free tier (`src/lib/ai/`), preferred over Claude when both keys are set. Free models regularly return 503 "high demand", so every call has a model chain (now three models, see below) and a hard deadline. Bulk scoring tries `gemini-3.5-flash-lite` first (about 1 s per 10 jobs). Resume reading, fit checks and company suggestions try `GEMINI_MODEL` (default `gemini-3.8-flash`, `thinkingLevel: low`) first, but only for 10-12 s: healthy, it answers in 4-9 s, while on a busy free tier it was measured taking 52-196 s. Raw REST with `responseJsonSchema` from zod; no SDK dependency.
- Resume text goes through `redactPersonalInfo` before any AI call (free-tier inputs may be used by Google): name line, full name, email, phone, street address, links and ZIP are removed. City and state stay. A surname or first name on its own stays too, because it could be an employer ("Ford", "Wells").
- Every fetched US job gets a match row; there's no keyword floor at storage. The list hides scores under 25 by default ("N weak matches hidden · Show"). Saving the resume or preferences re-ranks all stored matches right away (`rescoreStoredMatches`, keyword only); a refresh re-scores everything stored, not just what it fetched. Before this, profile edits only re-ranked jobs fetched again, and jobs that had been under the floor could never surface.
- Title similarity counts generic role words ("analyst", "engineer"…) at half weight, and caps a match at 0.15 when no field word matches, so "Credit Risk Analyst" isn't a "Security Analyst" match. "Cybersecurity" and "cyber security" compare equal. Security acronyms expand (SOC → security operations, GRC, IAM, DFIR, CTI…), and a different security word in the job title earns 60% credit ("SOC Analyst" ≈ "Cyber Defense Analyst"); the 0.15 cap still applies to every other field.
- Years of experience and clearance are parsed from descriptions at fetch time into `jobs.min_years` and `jobs.clearance`, and refreshed on every fetch (the upsert used to touch only `last_seen_at`). Level = the more senior of the title's level and the years asked for (0-2 entry, 3-4 mid, 5-7 senior, 8+ lead); 843 of 1,148 stored postings state years. Seniority penalties are one-sided: one level up −5, two or more −12 per level, and the reason leads with "Asks for 5+ years".
- Clearance: "active" (must already hold one) vs "obtain" (sponsored), tuned on live Leidos/GDIT/Booz Allen postings, where 57 of 74 cyber analyst roles needed an active clearance. Without `profiles.has_clearance`, an active requirement costs 40 raw points (a perfect fit lands under 50) and the AI is told the same, since the clearance line is often past the 2,500 characters it reads. USAJobs is exempt: agencies sponsor clearances after the offer.
- Skills match through aliases and without the cert vendor ("CompTIA Security+" ↔ "Sec+", "Entra ID" ↔ "Azure AD"); the offline resume extractor knows ~70 security tools, frameworks and certifications.
- `profiles.exclude_keywords`: jobs whose title contains one of these words are dropped. The AI suggests them when reading a resume (other professions that share vocabulary: credit, securities, sales), and they're edited on the Resume page. Seniority words are refused in code, because they'd hide most of the market and scoring handles level.
- Sample jobs are only a local fallback. In production a search with no sources fetches nothing, and stored sample matches are removed.
- Greenhouse: when `location` is only a work arrangement ("Hybrid", "In-Office"; about 85% of Cloudflare's postings), the location comes from a "Job Posting Location" custom field or `offices`, with US cities first, because the parser reads the first one.
- AI scoring scores each company + title once and shares the result with its copies (one role posted once per city), saving free-tier quota.
- "Check my fit" results are cached per job in `fit_checks` until the profile changes, and they replace that job's match score. The page isn't revalidated after a check, so the card doesn't jump away mid-click.
- "Suggest companies": the AI proposes employers with a Greenhouse/Lever/Ashby slug, and each board is fetched live (Greenhouse without descriptions, for speed), trying the other two services when the suggested one has no such board. Only boards that exist are shown. "Matches" are US titles at 0.75+ similarity and not two or more levels above the profile.
- Gemini calls hedge instead of timing out: a model that fails is replaced at once, but a slow one keeps running, and after `hedgeAfterMs` the next model is asked too; the first valid answer wins, and nothing runs past the deadline. On 2026-10-20, 3.8 Flash returned 503 while Flash-Lite took 21-29 s, so the old 12 s per-attempt cut-off dropped an answer that was on its way. `gemini-3.1-flash-lite` is the third model in both chains (separate capacity; answered in ~5 s that day). 2.5 models return 404 for new keys. Bulk match scoring doesn't hedge (`hedgeAfterMs: null`): with two batch workers it could put six requests in flight against the free tier's per-minute limit, and a batch that runs out of time just keeps its keyword scores.
